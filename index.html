Product Overview

The Gyre Fabric

Gyre is a privacy-and-defense network fabric that does two jobs at once. Outbound, it dissolves a person into a crowd so no observer can link who you are to what you reach. Inbound, it hides and shields a system so its origin can't be found, targeted, or flooded. It builds on the field's strongest proven cores — the onion routing behind Tor, the mix strategy behind Nym — and integrates them in a way no single tool ships today. Every page shows the mechanism running live and puts it side-by-side with the industry system it improves on.

◢ GYRE FABRIC · LIVE
2 rotors · 13 dims · 6 additions
INBOUND ROTOR

Protect a system

Traffic flows toward an asset you own, and the threats are recon, targeting, and floods. Gyre never publishes the origin: clients reach it through a rendezvous relay, the reachable address keeps moving on a keyed schedule only authorized clients can follow, and admission is priced with proof-of-work so a flood gets expensive fast. Unlike a reverse-proxy CDN, no intermediary ever terminates your encryption — only the origin does.

OUTBOUND ROTOR

Protect a person

Traffic flows out toward services you don't own, watched by a capable observer. Gyre breaks the link between you and your destination the way a mix network does — layered onion encryption so no relay sees both ends, per-hop timing delays and shared cover traffic so an observer can't line up entry with exit. Where Tor offers one fixed low-latency path, Gyre adds a dial: spend a little latency for materially stronger timing resistance, only on the flows that need it.

01 · Architecture

Two directions of protection, one fabric

Gyre runs two rotors on one set of relays because protecting a system and protecting a person are different machines — the traffic flows opposite ways, so the entry and exit rules differ. Sharing one fabric isn't a gamble: it's exactly how Tor already runs client anonymity and onion-service origin-hiding on a single network. Gyre ships both rotors as first-class, integrated products.

live · traffic directions
Outbound: a person emits packets into the fabric toward services. Inbound: attackers approach a server and are absorbed by the shield.

Proven at scale

Tor already unifies both directions: clients get outbound anonymity, and onion services hide a server inbound via rendezvous points. A dual fabric isn't speculative — it's a pattern in production for millions of users. Gyre takes that pattern and tunes each rotor as its own product.

Why the rotors stay distinct

The mechanisms that protect a server — move the target, price the flood — would hurt a person, because address rotation links your sessions together. The mechanisms that hide a person — mix, delay, split — add latency a public service can't wear. Same relays, deliberately different rules at each end.

02 · Threat Model & Scope

The adversary we defend against — named up front

Serious privacy engineering starts by naming its limits and its adversary — the discipline behind Tor, Nym, and Signal alike. Gyre is explicit about three boundaries and the exact adversary it defends against, so every capability that follows is a measurable claim, tested against a defined threat — not a marketing one.

interactive · the trilemma
Drag the core. You can favour any corner — never all three at once.

① The anonymity trilemma

Strong anonymity, low latency, low overhead — any system gets about two. A proven result (2018), not a Gyre limitation: mixing that defeats correlation always costs latency or bandwidth. Our answer is to make the trade-off a per-flow dial instead of one fixed setting. Drag the triangle to feel it.

② The all-seeing observer

An adversary watching both ends at once correlates you by timing, however many hops sit between — true for Tor, Nym, and every low-latency network. Gyre targets a realistic partial observer (sees some links, not all), states it plainly, and measures exactly how it performs against that adversary.

③ The endpoint

A login, a browser fingerprint, or what you access can identify you above the network layer. No network fixes the endpoint — so Gyre ships endpoint hardening as part of the product (Addition 2), rather than pretending the network alone is enough.

Scope, stated up front

Gyre does not claim to beat an all-seeing observer at low latency — no low-latency system can. What it does claim, it measures. Everything past this page is a capability with a number attached and a named adversary it was tested against. That honesty is the product's foundation, not a footnote.

03 · Design Principle

Why IP rotation isn't anonymity

A common assumption is that cycling through thousands of IP addresses makes you untraceable. It doesn't. Rotation defeats rate-limits and IP bans — genuinely useful — but it does nothing against the attack that actually deanonymizes you: timing correlation. Gyre spends its effort where it counts, and points rotation at the one place it truly helps: inbound defense (page 05).

The client's IP changes constantly (top). The adversary ignores it and matches the rhythm at entry and exit — correlation locks regardless.

🔗

04 · What Anonymity Requires

Unlinkability + a crowd

Real anonymity has two ingredients, and neither is motion: no single party sees both ends, and you blend into a large anonymity set of others doing the same thing. This is the number that decides whether any anonymity network works — Gyre included — so we treat growing the crowd as a core part of the product, not an afterthought.

interactive · anonymity set
Anonymity set k = 1

Drag the crowd size

k = 1  ·  the reticle locks instantly

At k=1 you're the only mover — trivially tracked. As the crowd grows, identical agents fill in and the tracker loses lock. Anonymity is the size of the crowd.

Why the crowd is the whole game

A private network built for one person hides no one — every packet it emits is "definitely that one user." An anonymity network of one is a contradiction. So the hardest part isn't the code — it's the crowd. Gyre is engineered to borrow and grow one: uniform clients, shared cover traffic, a k-anonymity admission governor, and an inbound product that seeds the same relays.

The industry proof point

Tor deliberately pins your entry guard for months rather than rotating it — because rotating the entrance raises your odds of eventually hitting a malicious one. The best engineering here rotates less, not more. Gyre follows the same evidence.

Can't we just fake the crowd? — measured, in our own harness

The tempting shortcut is to inject synthetic traffic so a lone service looks busy. We tested it in gyre-sim. A crowd is independent originators, not traffic volume — and the two behave nothing alike:

Cover traffic is still worth wiring for unobservability (hiding when you send), but that is a different property from the anonymity set. The crowd stays the one thing code can't manufacture.

05 · Inbound Rotor

The Shield — protect a system

This is where rotation earns its keep. The origin is never exposed; the reachable surface keeps moving on a keyed schedule that legitimate clients track and attackers can't; floods are priced out with proof-of-work. Where a CDN defends a service by fronting it — terminating your traffic in its datacenters and seeing your plaintext — Gyre defends by hiding it, so no intermediary ever holds your keys.

live · moving target defense
The real endpoint hops every tick. The keyed client always lands on it; the attacker sprays decoys and misses.
🫥

Rendezvous authenticated + pooled

Clients meet the service at a relay. The origin IP is never published — nothing to DDoS or target directly. Cookies are authenticated (mutual challenge–response, so a leaked bearer cookie can't hijack the session), and the origin can park across a pool of k relays so a relay-targeted flood dilutes instead of landing.

🔀

Address hopping (MTD)

Entry addresses rotate via HMAC(key, window). Legit clients derive the live one; scanners see a shifting field of decoys.

⛏️

PoW admission wired + live

A real anti-replay gate now fronts the rendezvous relay: the server issues a fresh, expiring, single-use challenge (stateless, so flooding the issuer costs nothing), and refuses anything unsolved before it can park or splice. Demonstrated live — 50/50 no-proof connections refused, legit client admitted, parking bound held.

🎟️

Capability tokens

Blind-signed, unlinkable passes let pre-authorized clients skip the puzzle — revocable, without revealing who they are.

Attacker cost under load

Watch the puzzle difficulty climb as attack volume rises — the legit user's cost stays flat.

06 · Outbound Rotor

The Mixer — protect a person

Four mechanisms, each covering a distinct threat. Switch between them — every tab is a live animation of that layer. The onion core is the same idea Tor proved at scale; the mixing delay, shared cover traffic, and multipath split are precisely what Tor's fixed low-latency design leaves on the table. Together they turn "you → destination" into something a partial observer cannot reassemble.

live · onion routing
Layered encryption — each relay peels exactly one layer and learns only its neighbours. No hop sees both ends.

Separation of knowledge

Three hops, three encryption layers. The guard knows you but not your destination; the exit knows the destination but not you. We cap at 3 on purpose — deeper adds latency and more chances to hit a bad relay, for near-zero gain.

The adaptive lever

An interactive flow gets low delay + more paths; a messaging flow gets heavy mixing. The client chooses, and the choice is sealed inside the onion so the network can't read the flow class. Spend the anonymity budget only where it's needed — this is where "better performance" actually comes from.

07 · Combining Mechanisms

A matrix, not a deep stack

More layers is not more security. Layers only help when they're independent and cover different threats; stacking same-threat mechanisms adds latency, bugs, and new leaks — not safety. Gyre is deliberately a wide matrix of orthogonal defenses, each one the single best answer to a distinct threat, rather than a deep stack of redundant ones.

Redundant ≠ layered

Three mechanisms from the same class — say, three ways to obscure motion — are three locks that open with one key. Gyre adds a layer only when it covers a threat nothing else does. The coverage map on the next page tracks exactly which dimensions are closed and which stay open.

The goal is cost, not "impossible"

Security is economics: raise the attacker's cost above the target's value, for a defined adversary. Even Tor caps its onion at 3 hops for this reason. Fewer, orthogonal, auditable beats deep, redundant, slow — every time.

08 · Mechanism Classes

Thirteen dimensions, one class each

Every privacy mechanism hides one dimension of the signal you emit — content, path, timing, appearance, and so on. Two mechanisms are the same class when they hide the same thing. Gyre maps thirteen such dimensions and covers them honestly. Ten are covered — built, tested, and wired into the running fabric (private PIR lookups; forward-secret, per-context sessions). One is partway: steganography's transport is wired, but that is plumbing, not deniability — real deniability needs a real cover the fabric can't supply. And two, we will not pretend to have closed: the crowd is a social/adoption constraint no code manufactures, and the endpoint falls to a compromised device regardless of the network. Claiming those two would be the one overclaim that discredits the honest twelve.

09 · What We Build On

Built on proven systems, not from scratch

Gyre doesn't invent new cryptography — it integrates the field's most studied systems and avoids their known dead-ends. Each rotor reuses a battle-tested core; the value is in how they're combined. Here's the prior art we stand on.

🧅

Tor — onion routing

3 fixed hops, layered encryption, volunteer relays across jurisdictions. Our separation-of-knowledge baseline.

🧄

I2P — garlic routing

Separate inbound/outbound tunnels on different paths — closest to "branches that aren't connected."

🌀

Mixnets — Chaum → Nym, Loopix

Batch, delay, reorder, cover traffic. The mixing strategy, done right — the honest price is latency. This is Gyre's outbound core.

💧

CoinJoin — Samourai's "Whirlpool", Tornado

Pool many users, shuffle, break input→output linkage. These tools already took the "whirlpool" name in the privacy space — which is exactly why this project is Gyre.

🔁

Rotating residential proxies

The "IP gyre" as it exists commercially — but sold for scraping, and the provider sees everything. Not anonymity.

🛰️

Moving Target Defense / SDN

Address-shuffling to protect servers. The correct home for the rotation instinct — our inbound rotor.

Gyre rides proven transports, proves its one novel core against a baseline before trusting it, ships the inbound rotor as a standalone product to seed the network, then layers the six additions by threat. Every step ends with a number — if it doesn't beat baseline, we learned cheaply. The core data plane and both rotors are already implemented and passing tests; what remains is scale, audit, and a crowd.

Why this order

  • Additions after the core is measured, each only when its threat is in scope — a matrix, not a deep stack.
  • Crowd (S12) last to build, first in importance — a fast, clever network with 50 users protects no one.

12 · Engineering Decisions

Decisions log

Every significant call in the design and the reasoning behind it — including the places where adversarial review forced us to downgrade a claim. This is the honest record. A credible security product shows its work, mistakes included.

D1
Two rotors, not one box. Inbound "protect a system" and outbound "protect a person" flow opposite ways and need different entry/exit rules. They share one fabric, proven possible by Tor onion services.
D2
Rotation is for defense, never anonymity. IP rotation defeats bans and rate-limits, and powers inbound MTD. It does nothing against correlation and links your sessions — banned from the outbound rotor.
D3
Anonymity = unlinkability + crowd. No hop sees both ends, and you hide in a large anonymity set. Motion is not an ingredient. A private network of one is a contradiction.
D4
Respect the trilemma; target a partial observer. We can't beat a global observer at low latency, so we don't pretend to. Adversary named up front; every metric measured against it.
D5
Onion for separation of knowledge — capped at 3 hops. Depth has diminishing returns and rising risk. The famous onion caps itself; so do we.
D6
Mixing + shared cover traffic fight correlation. Poisson delays and dummy loops (users as each other's noise) break timing linkage — the honest latency cost we accept.
D7
Erasure-coded multipath = the "branches" — corrected. Split each flow m-of-k across disjoint paths. Adversarial review downgraded this: it is probabilistic middle-path hardening vs a partial observer, NOT a reconstruction-threshold guarantee. An observer seeing 1..m−1 fragments still correlates by timing/volume/count without reconstructing, and disjoint paths widen endpoint exposure.
D8
Adaptive per-flow mixing = the performance lever. Latency-sensitive flows spend less budget; the choice is sealed inside the onion. Where "better performance" actually comes from.
D9
Inbound = rendezvous + MTD hopping + PoW + capability tokens. Hide the origin, keep the surface moving, price the flood, admit the trusted unlinkably.
D10
Combine orthogonally — a matrix, not a deep stack. One independent mechanism per distinct threat. "Impossible" is the wrong goal; raise attacker cost above target value for a defined adversary.
D11
Don't build crypto/transport from scratch. Ride WireGuard / Nym / Tor. Prototype one novel core, measure vs baseline, then expand.
D12
The crowd is the hardest problem. Incentives + Sybil resistance decide whether it works at all. Treated as first-class, not an afterthought.
D13
Add obfuscation / pluggable transport. Covers the "appearance" dimension so the fabric's traffic looks like random or ordinary HTTPS — an org can't block or flag you for using it. Cheap, high value.
D14
Endpoint isolation + data minimization. Closes the Achilles' heel that defeats every network layer: compartmentalized per-context identities, ephemeral keys, a hardened client, optional TEE for key ops. Nearly free, and it improves efficiency.
D15
Zero-knowledge / anonymous credentials. Upgrade capability tokens so clients prove authorization while revealing zero identity — unlinkable auth and a stronger Sybil story.
D16
Decentralization + attestation. No single coercible operator, and verifiable proof relays run honest code — the trust-locus dimension.
D17
Deniability / steganography — situational. Hides that you're using the fabric at all. Add only if the adversary punishes use itself; otherwise it's cost without benefit.
D18
PIR / ORAM for directory lookups — surgical. Hides what you look up. Default PIR OFF — full signed-consensus download beats PIR at Tor scale; reserve PIR for the inbound rendezvous-descriptor lookup, whose target genuinely leaks.
D19
Position as integration, not a record-holder. Verified: we can't beat VPN on speed, Tor/Nym on crowd, or Cloudflare on capacity. The defensible niche is the combination — a Tor-competitive outbound rotor with an honest mixing dial + an inbound rotor none of them integrate.
D20
Crowd bootstrap is the critical path — not crypto. Every competitor verdict is gated on concurrent set size. Levers: Loopix cover (effective set, mix-latency only), uniform client, k-anon governor, bridge-to-Tor to borrow a crowd, inbound-shield seeding. Cleverness never manufactures a crowd.
D21
Speed = FAST/MIX lanes + QUIC/MASQUE + AS-aware paths. An honest trilemma menu plus a near-Pareto transport win (kills cross-circuit head-of-line blocking). Honest verdict vs modern Tor (Conflux + congestion control already merged) is match / modest win, never "beat."
D22
Cloudflare compete = trust topology, for closed/enterprise tunnels. Win: no plaintext-terminating intermediary to compel. NOT open-web scrubbing — MTD ingress needs client-held keys so it only serves an authorized set, and we have zero L3/L4 volumetric defense.

The full rationale, real-world citations, and honest ceilings behind every decision live in the project's research record.

13 · Positioning

Where Gyre fits — honestly

Gyre is an integration play, not a record-holder. Against each category leader it competes on a specific, defensible axis — and we're precise about where that advantage ends. Each verdict below survived an adversarial review whose job was to strip overclaims, so "compete" means compete and "beat" means beat.

Positioning in one line

Gyre's edge is integration: a Tor-competitive outbound mixer with an honest latency dial, plus an inbound server-protection rotor none of the anonymity networks offer — unified on one fabric. It competes on trust and completeness, not raw speed or datacenter scale, and its real-world strength grows with the size of its crowd. That's a focused, defensible place to stand — and the rest of this page maps it competitor by competitor.

vs VPN

beat-partially · 84%

Edge: distributed trust — 3-hop Sphinx, no single operator sees both ends or can be compelled; plus mixing + cover a VPN has zero of; plus an inbound rotor and a censorship-resistant transport.

Boundary: a VPN still wins on latency, throughput, battery, and setup — that's the cost of three hops. Gyre competes on trust and correlation-resistance, not raw speed.

vs Tor

compete · 78%

Edge: an optional per-flow Poisson mixing dial (stronger vs the timing observer, at honest latency cost); QUIC/MASQUE transport + latency/AS-aware path selection close default-Tor's gap.

Boundary: on speed we match or modestly edge modern Tor (which already merged Conflux + congestion control) — not "beat." Tor's crowd is its decisive advantage; we compete, we don't surpass it.

vs Nym

beat-partially · 60%

Edge: the inbound server-protection rotor — Nym is outbound-only, so on inbound we win by default (rendezvous + MTD + PoW admission + tokens).

Boundary: on pure outbound mixnet anonymity Nym leads today — live crowd, token incentives, mainnet, audits. Our win is the inbound rotor it lacks; on outbound we compete, and we corrected two claims (multipath, the sealed knob) early review overstated.

vs Cloudflare

beat-partially · 74%

Edge: trust topology — TLS/Noise terminates only at the origin, so no intermediary sees plaintext or can be compelled; a reverse-proxy CDN structurally can't offer this. Plus origin-hiding + load-scaled PoW admission + Privacy-Pass tokens (SHA-256 default puzzle, with a memory-hard Equi-X option behind an opt-in feature).

Boundary: Cloudflare's anycast scrubbing capacity is out of reach — Gyre offers no L3/L4 volumetric defense. Because MTD ingress needs client-held keys, it fits authenticated and enterprise tunnels, not open-web shielding.

How we keep our claims honest — the discipline every statement in this deck is held to

  • Never say "beat Tor on speed" unqualified — say "match / modest win vs modern Tor."
  • Never sum inbound-protected clients into the outbound anonymity-set number.
  • Never quote a cover-inflated "effective set" as if it were concurrent real senders.
  • Loopix global-observer resistance holds only at mix latency, never low latency.
  • Multipath = probabilistic middle-path hardening, not a reconstruction threshold.
  • "Unblockable" is banned — obfuscation buys "costlier to block than the censor will pay today"; obfs4's random bytes are now a positive entropy-DPI fingerprint.
  • Anonymous credentials / staking add zero intrinsic Sybil resistance — the scarce resource (PoW / stake) does; staking = wealth concentration, not user-decentralization.
  • Reproducible builds prove binary = source, not that a relay actually runs that binary.

Full designs, real-world citations, and the honest boundary for every comparison live in the project's research record.

Tor does this. Gyre does this instead.

The clearest way to understand Gyre is next to the system most people already know — Tor, the onion network behind Tor Browser. They share the same DNA: three hops, layered encryption, distributed trust, no single relay that sees both ends. We compete on the mixing dial and the inbound rotor; we don't pretend to have Tor's anonymity set yet.

16 · Protection Model

What it protects — and for whom

The two rotors look symmetrical on an architecture diagram. They are not. One of them has a security argument that survives having zero users; the other is worth almost nothing without a crowd. That asymmetry is the single most important fact for anyone deciding where this can be tested, and it comes from the project's own measurements rather than from a preference.

Inbound · protect a system

Security comes from cost and topology — an unpublished origin, a keyed schedule, a puzzle price. None of those mechanisms mentions an anonymity set.

Crowd dependency: none. The proof-of-work asymmetry is a property of SHA-256; it is identical for one client and one million. The origin's IP is unpublished because it only ever dials out — a topological fact, true with exactly one user.

Outbound · protect a person

Security comes from being indistinguishable from other people. There is no substitute, and no amount of code manufactures one.

Crowd dependency: total. Measured: at 4 concurrent flows, even the strongest usable mixing leaves an optimal attacker at 0.719 accuracy. The mechanism is not weak — the haystack is.

!
Why growing the crowd does not fix the mixer. Between 4 and 150 concurrent flows at identical 150 ms/hop mixing, attacker accuracy falls 0.719 → 0.063 — an 11× improvement that looks like progress. But chance falls 0.25 → 0.0067, a 37× improvement. The ratio of accuracy to chance does not fall; it rises, 2.9× → 9.5×, then flattens. The attacker stays roughly an order of magnitude better than guessing at every crowd size measured. Mixing changes how hard each guess is. Only a crowd changes how many guesses there are. The code supplies the first; it cannot supply the second.

"What about DDoS?" — the honest taxonomy

This is the most common question and the most common way privacy tools overclaim. DoS is not one attack — it is a stack, and Gyre sits at a specific, defensible layer of it. Told straight:

Attack classExampleCan Gyre help?
Volumetric flood (L3/L4)UDP/SYN/amplification — saturate the pipeNo, and never. This is capacity — anycast scrubbing. A full pipe is physics; no proof-of-work changes it. That is Cloudflare / AWS Shield, not us (D22).

Each admission costs the attacker real work; the server checks it in one HMAC + one hash. The gate fronts the rendezvous relay and refuses a flood live — 50/50 unsolved connections dropped.

The honest sentence is now: "the inbound rotor is the only half whose security argument survives zero users — and, for everything but MTD, it is deployable today."

Still absent, by design and by physics: no volumetric L3/L4 DDoS defence of any kind (decision D22) — a flood that saturates the link wins before any puzzle is read. MTD serves a closed, authorized client set only, so it can never front an open web service. The default puzzle is SHA-256, the most ASIC/GPU-friendly choice — but the memory-hard Equi-X alternative Tor deployed for exactly this reason is now wired through the gate behind an opt-in --features equix (its LGPL isolated to builds that enable it; the pure-MIT default is untouched), and an adversarial review of the wiring found nothing. The puzzle is also a real admission protocol, not just a cost function: server-issued, expiring, single-use — a replayed solution is refused (shown live above).

17 · Deployment & The Ask

Where this can honestly be tested

The instinct is to ask for a big server and "run the network on it." That instinct produces a demo that measures nothing, and a senior engineer will see through it in one question. The useful ask is different, smaller, and defensible — and it starts by conceding the point before it is made.

✕
One machine can never be a deployment. Onion routing's only security assumption is that no single party holds every relay's key. Co-locating every relay collapses that to one party with root, so anonymity against that operator is not degraded — it is zero, by construction, at any mixing setting. Three things in this codebase make that concrete rather than theoretical: the per-hop delay is a sealed instruction the relay decrypts and obeys, so anyone reading process memory reads the whole schedule; cover traffic is the literal ASCII string gyre-cover-loop; and in the shipped testnet binaries every relay secret key is derivable from its public label with a published salt. And to an external observer, one host means one interface emitting and receiving — the guard/exit distinction collapses and coverage is 1.0 for free, which is the worst row in our own table.
✓
But that is exactly what makes it a legitimate simulator host. Under a simulator the co-location is irrelevant — the adversary is simulated too. A result from it is a claim about the design, not about a running system. That single distinction is the difference between a credible ask and a laughable one, and it should be said out loud, first, unprompted.

The ask, stated as arithmetic

The harness cost fits t(n) = 7.81 ms·n + 0.573 ns·n³ to within 1% at every measured point — the linear term is real Sphinx crypto, the cubic term is the Hungarian solver. So the request is not a vibe, it is a division:

10⁴flows — demonstrated today (partial observer, ~1 min)
10⁵the next target — the axis published work reaches
O(n³)the Hungarian matcher — all-watched at 10⁵ is where cores earn their keep

Ask for CPU cores and system RAM on a Linux box. Explicitly not GPU time. A DGX is a GPU machine, and the workload here is Shadow's syscall interception plus X25519 and ChaCha — none of which has a GPU path. Asking for a DGX cluster to run this would itself be the kind of overclaim the whole project exists to avoid. The split is simple: gyre-sim wants cores; Shadow wants RAM, cores second.

✓

What to promise

Simulation scale, and a published number with error bars that a third party can reproduce in one command. A regression gate that catches an anonymity change before it ships.

✕

What never to claim

Anonymity, protection of anything real, or that the machine "runs the network." Nothing on that box is reachable from outside, and nothing it produces is a security result about a deployed system.

The sentence that makes the ask work. "A mixnet on one machine has zero anonymity against that machine's operator — which is exactly why the machine can only ever be a simulator. I'm not asking to deploy anything. I'm asking to measure at scale — the testbed already runs a realistic crowd to 10⁴ flows across cores, and I want to reach 10⁵ — against an attacker I already built and verified against brute force. It already told me my own published headline was 4.5× too optimistic, and I retracted it."
